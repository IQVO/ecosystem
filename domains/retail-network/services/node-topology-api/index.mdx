## Purpose
The authoritative registry of the network's physical shape: every node (vendor fulfillment centres, cross-docks, returns centres, and the network's own sortation centres, delivery stations and air hubs), its declared operational profile, the directed lanes between nodes, the regions, and which delivery station serves which postal area.

|---|---|
| Bounded context | `node-topology` |
| Domain | Retail Network (`retail-network`) |
| DDD classification | Supporting |
| Tier | Retail Network, logistics tier |
| Repository | [IQVO/node-topology](https://github.com/IQVO/node-topology) |
| Events | [node-topology](/docs/services/node-topology) |

This service groups the context's synchronous surface: the OLTP REST API (`openapi.yaml`) and, where the
context has one, the separate read-only reports API (`openapi-reports.yaml`) served by its `*-reports`
binary from an isolated analytical database. Endpoints are unauthenticated fleet-wide.


REST contract of the node-topology bounded context of the retail network, derived from retail-network-docs model/model.yaml (contexts[node-topology].rest, .aggregates, .publishes, conventions.errors). Node Topology is the authoritative registry of nodes, their declared operational profiles, lanes, regions and service areas. vendor-connectivity calls POST /nodes and PUT /nodes/\{nodeId\}/operational-profile in-organization while it processes vendor submissions; the network-ops planner calls the other write routes and may also declare a network node's profile (declaredBy NETWORK_OPS); any context may call the read routes. No authentication, consistent with the fleet. Errors are RFC 9457 problem details. The shared problem types are not-found (404), illegal-transition (409), concurrent-update (409) and validation-failed (422).
