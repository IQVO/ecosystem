## Purpose
Knows what the network can sell and from which node: the catalogue item, one listing per (catalogue item, node), and the quantity each node currently claims it can ship, with the basis the vendor gave for that number (physical stock or throughput-constrained).

| | |
|---|---|
| Bounded context | `offer-availability` |
| Domain | Retail Network (`retail-network`) |
| DDD classification | Supporting |
| Tier | Retail Network, commerce tier |
| Repository | [IQVO/offer-availability](https://github.com/IQVO/offer-availability) |
| Events | [offer-availability](/docs/services/offer-availability) |

This service groups the context's synchronous surface: the OLTP REST API (`openapi.yaml`) and, where the
context has one, the separate read-only reports API (`openapi-reports.yaml`) served by its `*-reports`
binary from an isolated analytical database. Endpoints are unauthenticated fleet-wide.


REST contract of the offer-availability bounded context of the retail network, derived from retail-network-docs model/model.yaml (contexts[offer-availability].rest, .aggregates, .publishes, conventions.errors) and adjusted by the final cross-context decisions (Gap Register G23 and G24). The context owns the catalogue items, one listing per (catalogue item, node) and the vendor-declared available quantity of each listing with its basis. POST /inventory-feeds is an in-organization call made by vendor-connectivity while it processes a vendor's inventory submission; vendors never call this API directly. Network merchandising calls the catalogue and listing writes; the storefront reads GET /catalog (Open Host Service). No authentication, consistent with the fleet. Errors are RFC 9457 problem details. The shared problem types are not-found (404), illegal-transition (409), concurrent-update (409) and validation-failed (422); the others are this context's invariants, one slug per model Err name.
