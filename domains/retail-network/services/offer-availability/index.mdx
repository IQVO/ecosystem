## Purpose
Knows what the network can sell and from which node: the catalogue item, one listing per (catalogue item, node), and the quantity each node currently claims it can ship, with the basis the vendor gave for that number (physical stock or throughput-constrained).

Every message is a CloudEvents 1.0 structured-mode JSON document (`application/cloudevents+json`).
`<ctx>.events` topics carry the integration contract; `<ctx>.analytics` topics carry projector input for the
context's own reports and are never consumed by another context.

## Contract


Event catalog for the **offer-availability** bounded context of the retail
network (commerce tier): the network's catalogue items, one listing per
(catalogue item, node) and the quantity each node claims it can ship, with
the basis the vendor gave (ADR 0001, ADR 0002).

**Published.** Nine events, all integration events on the topic
`retailnetwork.offer-availability.events`, through a **transactional
outbox**: the aggregates and their already-encoded events are written in ONE
database transaction and an always-on relay drains them to Kafka
(at-least-once; the CloudEvents `id` is stored with the outbox row, so a
retry republishes the same `id`). The nine types are catalogued in ADR 0004.
A listing created on a node that is not sellable raises ListingCreated and,
in the same transaction, ListingSuppressed (ADR 0002, A6), so a consumer
never has to guess the initial state.

**Consumed.** Four node-topology events (`NodeRegistered`, `NodeActivated`,
`NodeSuspended`, `NodeRetired`) from `retailnetwork.node-topology.events`,
in the consumer group given by `NODE_STATUS_CONSUMER_GROUP` (proposed value
`offer-availability-node-status`). They feed the local NodeStatusView and
drive the SuppressOnNodeUnavailable policy (ADR 0003). The consumer
dispatches on the full `type`, ignores every other type, tolerates unknown
fields, and dedupes on the CloudEvents `id` (inbox table `processed_events`).

**Analytics.** The model names no analytics-only event for this context, so
nothing is published on `retailnetwork.offer-availability.analytics`.

**Envelope (mandatory).** CloudEvents 1.0, structured content mode, Kafka
header `content-type: application/cloudevents+json; charset=UTF-8`.
`specversion`, `id`, `source` (`/retailnetwork/offer-availability`), `type`,
`subject` (the aggregate root id), `time`, `datacontenttype`
(`application/json`) and `dataschema`
(`urn:retailnetwork:offer-availability:events:<EventName>:v1`) are all
required. Kafka key = the subject, so one aggregate's events stay ordered on
one partition. Type =
`com.retailnetwork.commerce.offer-availability.<entity>.<EventName>` with
entity `catalogitem`, `listing` or `inventoryfeed`. A breaking payload
change is a new `.v2` type, never a mutation. Dispatch on the full `type`,
ignore unknown types, dedupe on `id`.

**Conventions.** `data` is camelCase; ids are strings; timestamps are RFC
3339 UTC; counts are integers; enums are UPPER_SNAKE; optional fields are
omitted when unset (never null).
