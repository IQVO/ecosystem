## Overview
The carrier webhook of CARRIER_HANDOFF service areas. Unauthenticated by the standing fleet decision, exactly like POST /journeys/\{trackingNumber\}/scans (the per-carrier token scheme is a recorded follow-up). Each report becomes one scan with scanId "&lt;carrierId>:&lt;carrierEventId>", so a re-sent report answers 409 duplicate-scan. PICKED_UP is the handoff at the journey's handoff node (a journey already WITH_CARRIER is a no-op that answers 200); OUT_FOR_DELIVERY, DELIVERED and DELIVERY_FAILED become their scans; IN_TRANSIT is accepted and counted without a scan. A refusal that keeps the scan (scan-out-of-order, illegal-transition) is stored under the Idempotency-Key together with the scan and replayed on a retry.




## POST `(/carrier-events)`

### Parameters
- **Idempotency-Key** (header) (required): Client-generated key, 1-128 printable ASCII characters, one per logical submit (a retry reuses it). A retry of the same request under the same key replays the first answer (24 hours, Idempotency-Replayed true) only when that answer is final for the request, that is a success, the refusals not-found, label-already-issued, void-after-handover, journey-closed and duplicate-scan (a function of the request or of a fact that never reverts), and scan-out-of-order and illegal-transition (the scan was stored, not applied, and stays stored). Every other refusal follows state that can change and is NOT stored; the key is released and a retry with the same key executes again, namely validation-failed, address-suspect, pickup-point-unavailable, destination-prefix-unavailable, tracking-number-taken, concurrent-update, and every 5xx. After a release, another body under the same key is a new request. The same key with a different method, path or body, while an answer is stored for it, answers 409 idempotency-key-reused.
