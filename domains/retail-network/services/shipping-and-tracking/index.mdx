## Purpose
Issues shipping labels (the only place outside customer-ordering that ever sees a ship-to address) and owns each package's journey: one customer-visible timeline consolidated from vendor handover, load and delivery facts, ending in delivered, returned or lost.

Every message is a CloudEvents 1.0 structured-mode JSON document (`application/cloudevents+json`).
`<ctx>.events` topics carry the integration contract; `<ctx>.analytics` topics carry projector input for the
context's own reports and are never consumed by another context.

## Contract


Event catalog for the **shipping-and-tracking** bounded context of the retail
network (logistics tier): it issues shipping labels and owns each package's
journey, the one customer-visible timeline consolidated from vendor handover,
load and delivery facts (ADR 0001, ADR 0002).

**Published.** Eight events, all on `retailnetwork.shipping-and-tracking.events`,
through a **transactional outbox**: the aggregate rows and their already-encoded
events are written in ONE database transaction and an always-on relay drains
them to Kafka (at-least-once; the CloudEvents `id` is stored with the outbox row,
so a retry republishes the same `id`). The eight types are catalogued in ADR 0004.
Every one is an integration event: the model's analytics-only events
(LabelVoided, PackageReturned, PackageLost) were promoted by contracts-delta
E6 and E16, so nothing is published on `retailnetwork.shipping-and-tracking.analytics`.
No event carries a ship-to address or any part of it (the opaque `stopKey` and the
postal prefix on LabelIssued are the only derived values; ADR 0002 A9, A10).

**Consumed.** Seven types from four topics (ADR 0003): vendor-connectivity
VendorShipmentConfirmed, linehaul-transportation LoadDeparted and LoadArrived,
last-mile-delivery PackageOutForDelivery, DeliveryAttempted and
PackageReturnInitiated, offer-availability CatalogItemCreated. Each consumer
group dedupes on the CloudEvents `id` (inbox table `processed_events`),
dispatches on the full `type`, ignores unknown types and fields, and parks a
poison message on a dead-letter topic.

**Envelope (mandatory).** CloudEvents 1.0, structured content mode, Kafka
header `content-type: application/cloudevents+json; charset=UTF-8`.
`specversion`, `id`, `source` (`/retailnetwork/shipping-and-tracking`), `type`,
`subject` (the aggregate root id), `time`, `datacontenttype` (`application/json`)
and `dataschema` (`urn:retailnetwork:shipping-and-tracking:events:<EventName>:v1`)
are all required. Kafka key = the subject, so one aggregate's events stay ordered
on one partition. Type = `com.retailnetwork.logistics.shipping-and-tracking.<entity>.<EventName>`
with entity `label` or `journey`. A breaking payload change is a new `.v2` type,
never a mutation.

**Conventions.** `data` is camelCase; timestamps are RFC 3339 UTC; optional fields
are omitted when unset; arrays are always present.
