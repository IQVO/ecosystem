## Overview
Asynchronous (`SubmissionKind` `RETURN_OUTCOME`). The authorization must be
known and still `AUTHORIZED`, `nodeId` must be the advice's node and belong to
the vendor. Lines the advice never authorized are reported, never refused
(goods on the dock are never turned away); the network records them as
unexpected and restocks nothing of them. On `202` the advice leaves the poll
and the network publishes `VendorReturnOutcomeSubmitted`.





## POST `(/vendor/return-outcomes)`

### Parameters
- **Idempotency-Key** (header) (required): Client-chosen key, 1 to 128 printable ASCII characters (`400 idempotency-key-required` when absent, `400 idempotency-key-invalid` when malformed). A retry with the same key, method, path and body returns the first response with `Idempotency-Replayed: true` when that response is stored: every 2xx, and the refusals that are final for the request (`partial-acknowledgement`, `ack-window-closed`). Every other refusal is NOT stored and its key is released, so the same request under the same key executes again and a different body under that key is a new request: `validation-failed`, `ack-window-out-of-range`, `not-found`, `node-not-owned-by-vendor`, `vendor-suspended`, `already-acknowledged`, `label-before-acceptance`, `confirm-without-label`, `illegal-transition` and `concurrent-update` (retry the same key once the state changed), and every 5xx (`upstream-unavailable`, `upstream-refused`). While the key is stored, the same key with a different method, path or body is `409 idempotency-key-reused`.
