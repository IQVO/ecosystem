## Purpose
The read side of browsing and search: one ProductView per catalogue item (title, flags, content, categoryId, list and effective price, inStock, purchasable; the category path is joined from CategoryView at query time) and one CategoryView (tree plus purchasable counts), fed by events from offer-availability, product-content and pricing, searched with PostgreSQL full-text search and pg_trgm (D9), behind a port so a dedicated engine is a later adapter swap.

This service groups the context's synchronous surface: the OLTP REST API (`openapi.yaml`) and, where the
context has one, the separate read-only reports API (`openapi-reports.yaml`) served by its `*-reports`
binary from an isolated analytical database. Endpoints are unauthenticated fleet-wide.


REST contract of the product-discovery bounded context of the digital storefront (storefront model, contexts[product-discovery].rest). Discovery is the read side of browsing and search (no aggregate in v1): ProductView per catalogue item (title, flags, content, category path, list and effective price, inStock, purchasable) and CategoryView (tree plus purchasable counts), fed by events from offer-availability, product-content and pricing. Search ranks title (A), category names (A), attributes (B) and description (C) in a PostgreSQL tsvector with a GIN index, with pg_trgm similarity as the typo fallback; facets are category, price band and in-stock; product-type queries also return category suggestions. Errors are RFC 9457 problem details (application/problem+json); this read-only surface uses not-found (404) and validation-failed (422), plus 400 problems for paging (invalid-limit, invalid-cursor, unknown-query-parameter). No authentication. A catalogue item the item master has not announced yet (a stub row) is invisible: GET /products/\{id\} answers 404 for it and search never lists it. The category path of a product is joined from the CategoryView at query time, so a category rename shows at once without re-indexing products.
