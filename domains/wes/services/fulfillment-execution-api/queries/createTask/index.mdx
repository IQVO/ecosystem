## Overview
Puts a new unit of Pick, Pack, or SLAM work into the pending pool. The task is not assigned to any station at creation time — PULL dispatch (`POST /stations/{stationId}/claim-next`) is the only way a task becomes claimed, consistent with this service's rule that work is never pushed to a named station in advance. `cpt` (Critical Pull Time) drives dispatch priority: `claimNext` always selects the earliest-CPT pending task a station is equipped for.

**Idempotent per `Idempotency-Key` (ADR-0028).** Send a caller-chosen `Idempotency-Key` header on every call. The first request with a given key creates the task; a retry with the same key and the same body replays the stored response verbatim (same status, headers and task id — including a cached 4xx) instead of creating a duplicate. Reusing a key with a different body is rejected with `422 idempotency-key-reused`; omitting the header is `400 idempotency-key-required`. (Key enforcement requires the Postgres-backed deployment; the in-memory development configuration skips it.) Without a repeated key every call creates a new task with a fresh, server-generated id.





## POST `(/tasks)`

### Parameters
- **Idempotency-Key** (header): Caller-supplied unique key (e.g. a UUID) identifying this creation attempt. **Clients must always send a non-empty key**: a Postgres-backed deployment rejects a missing key with `400 idempotency-key-required` (the in-memory development configuration ignores the header, which is why the schema marks it optional). Retries of the same logical request must reuse it; a genuinely different request must use a new one.
