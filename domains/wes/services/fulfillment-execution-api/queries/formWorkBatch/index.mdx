## Overview
Pick batching behind the `PICK_BATCH_MODE` rollout gate. The anchor is exactly the task `POST /stations/{stationId}/task-claims` with `taskType: PICK` would return (the same claimer selects it), so batching never changes who goes first; companions are the station's interleaving-hint candidates inside the anchor's CPT band, in hint rank order, kept only when the station can do them and the cart segregation matrix allows sharing, up to the configured maximum (default 4). A batch of one is valid; nothing waits for a batch to fill. With the mode not `on` (the fleet default is `off`) the surface answers 503 batch-mode-off and `task-claims` is the only dispatch path, exactly as before.





## POST `(/stations/{stationId}/work-batches)`

### Parameters
- **Idempotency-Key** (header) (required): Caller-supplied key, 1-128 printable ASCII characters (a UUID minted once per LOGICAL submit; a retry reuses it, a new user action mints a new one). Required on every POST: a missing key is `400 idempotency-key-required`, a malformed one `400 idempotency-key-invalid`. The key is global to the service: a retry with the same method, path and body replays the stored answer (status, body and `Location`) with `Idempotency-Replayed: true` and runs nothing; the same key with a different method, path or body is `409 idempotency-key-reused`.

- **stationId** (path) (required): The station forming its walk, e.g. as registered via `POST /stations`.
