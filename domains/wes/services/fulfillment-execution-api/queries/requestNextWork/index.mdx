## Overview
The PULL side of the execution/planning seam (ADR-0058): execution, whose claimable queue for a process path is draining, delegates "admit the next priority-ordered unit" to the wes-work-planning A2A agent. Planning keeps every release decision (release policy, WIP invariant); execution keeps the judgement of when to ask. The authoritative fact still arrives as the `WorkReleased` CloudEvent on Kafka through the existing consumer — the 200 body is only the delegation acknowledgement. Each call asks for exactly one unit, so the endpoint is deliberately NOT idempotent and NOT behind the idempotency middleware: repeating the request is a legitimate second pull. Answers 503 when this deployment has no `WORK_PLANNING_A2A_URL` configured, and 502 when the planning agent is unreachable or answers off-contract.





## POST `(/paths/{pathId}/work-requests)`

### Parameters
- **Idempotency-Key** (header) (required): Caller-supplied key, 1-128 printable ASCII characters (a UUID minted once per LOGICAL submit; a retry reuses it, a new user action mints a new one). Required on every POST: a missing key is `400 idempotency-key-required`, a malformed one `400 idempotency-key-invalid`. The key is global to the service: a retry with the same method, path and body replays the stored answer (status, body and `Location`) with `Idempotency-Replayed: true` and runs nothing; the same key with a different method, path or body is `409 idempotency-key-reused`.

- **pathId** (path) (required): The process path more work is requested for (e.g. pick-zone-a). Must be a path Work Planning knows; an unknown path answers 404.
