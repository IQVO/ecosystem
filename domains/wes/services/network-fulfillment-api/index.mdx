## Purpose
Anti-corruption layer between the fleet and an external retail fulfillment network (Amazon Selling Partner API): network-originated demand, the acknowledgement clock and capacity-aware advertised availability.

| DDD classification | Supporting |
| Tier | WES, external network edge (anti-corruption layer) |
| Repository | [IQVO/network-fulfillment](https://github.com/IQVO/network-fulfillment) |
| Events | [network-fulfillment](/docs/services/network-fulfillment) |

This service groups the context's synchronous surface: the OLTP REST API (`openapi.yaml`) and, where the
context has one, the separate read-only reports API (`openapi-reports.yaml`) served by its `*-reports`
binary from an isolated analytical database. Endpoints are unauthenticated fleet-wide.


The Anti-Corruption Layer between this platform and an external retail fulfillment network (Amazon's Selling Partner API, Vendor Direct Fulfillment). It owns **NetworkOrder**: demand that arrived from outside carrying a deadline we did not choose, and the answer we owe the network by a deadline the network set.

**This surface is READ-ONLY apart from ONE explicit write endpoint, and that is a design decision rather than an omission.** Demand enters this context by POLLING the network and by nothing else: the network offers us no push, so an HTTP intake endpoint would be a second, fictional inbound path with no counterpart in production. The only thing such an endpoint could honestly be used for is injecting test demand, and the stub gateway's file-seeded mode (`NETWORK_SEED_FILE`) already does that without pretending to be a protocol. The one write is `POST /network-orders/{networkRef}/shipment-confirmation` (ADR 0014): a fact this context is TOLD (an order shipped), not demand it decides on.

So what is exposed here is OBSERVATION, answering the two questions an operator actually has during an incident: *what did we tell the network about purchase order X*, and *is the inbound leg alive*. The second matters because the poller's failure mode is silence — a poller that stops fetching produces no orders, no errors and a perfectly healthy `/healthz`, while the 24-hour acknowledgement clock keeps running against wall time. A poller outage is an SLA breach, not a delayed batch.

**Customer PII stops in this context.** Ship-to name, address and phone live here and nowhere else in this platform, and no response in this document carries them. The network's own *references* (its purchase-order number, its line references, its product identifiers) ARE exposed, because the questions above are unanswerable without them — those identify the order, not the person.

Feasibility is never computed here. Whether a deadline can be met is asked of order-management's promise policy, which owns that arithmetic for the whole platform; this context asks, records the verdict, and answers the network accordingly.
