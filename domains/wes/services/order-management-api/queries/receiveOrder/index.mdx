## Overview
Intake — the ReceiveOrder use case. Validates every requested line (SKU non-empty, quantity > 0), mints an `OrderId`, and persists the order in `Received` status, publishing `OrderReceived` unconditionally.

Immediately afterward, in the SAME call, this service attempts allocation-then-release: it reserves stock per line via inventory-storage's `POST /reservations` (see the Allocation tag), and for every line that ends up `Allocated` and eligible under BR3 (see below), releases it — announced via the enriched `OrderAllocated` / `OrderPartiallyAllocated` Kafka events, never a second synchronous call. If that implicit allocation attempt hits a hard (non-business) failure, this endpoint still returns `201`: the order genuinely was received, and a caller expressing "place an order" must never be told that failed just because an internal, best-effort next step could not complete. The returned body reflects whatever the allocation pass actually achieved.

`allowPartialShipment` defaults to `false` — ship-complete (BR3). Every line's `pathId` is chosen by this service, not the caller (ADR 0021): the active process paths in the process-path catalogue are filtered by their declared eligibility and the shortest known cycle time wins (ties: lower path id), falling back to the default `pick` when no catalogue is configured or no path is active. A caller placing an order has no business supplying wes-work-planning's process-path vocabulary at intake; `pathId` is visible on every line in the response, but not settable on the request.
