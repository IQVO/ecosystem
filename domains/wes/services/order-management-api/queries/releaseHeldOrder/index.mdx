## Overview
The ReleaseHeldOrder use case (ADR 0020). Commits an order received with `releaseOnAllocation: false` to the floor: its already-allocated lines are released through the same BR3-gated flow every other release uses, the promise is recomputed by the same policy, and the same `OrderAllocated`/`OrderReleased` events fire with the same per-line payload.

IDEMPOTENT for a HELD order: releasing one whose lines are already released returns `200` with no state change and no event. A caller working against an external fill-or-kill deadline cannot distinguish "my release was lost" from "my release failed", so retrying must be safe.

An order that was never held has nothing to release on demand — its lines release themselves at allocation — so calling this on one is rejected with `409` rather than silently succeeding, since it means the caller has the wrong order id or the wrong expectation. This holds even when that order has no allocated lines of its own (a backordered order, say): "never held" and "already released" are different answers and must not collapse into one.
