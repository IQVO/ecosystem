## Overview
The RetryAllocation use case. Re-attempts allocation for the order's `Backordered` lines and ONLY those lines — it is the single sanctioned route from `Backordered` back to `Allocated`, and it is what unblocks a ship-complete order held back by BR3. UNLIKE the implicit allocation attempt folded into `POST /orders`, this is an explicit, on-purpose operator/recovery action: a hard (non-409) failure here fails the call with `503` rather than being swallowed — invoking this endpoint IS asking for allocation right now.

A line still short of stock stays `Backordered` (no error). The same fail-closed rule as intake's implicit allocation applies to any non-409 failure. An order with no backordered line at all is rejected with `409`: retrying an order that is not backordered is a caller mistake, not a no-op.

On success, this ALSO attempts release in the same call — the same allocation-then-release flow `POST /orders` uses — announced via the enriched `OrderAllocated` / `OrderPartiallyAllocated` Kafka events rather than any synchronous call to a Supplier.
