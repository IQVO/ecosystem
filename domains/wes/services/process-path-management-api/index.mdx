## Purpose
Operator-configurable process-path topology (id, capability requirements, activation lifecycle, CPT schedules), replacing a static YAML catalogue. Source of the process-path published language for the fleet.

| | |
|---|---|
| Bounded context | `process-path-management` |
| Domain | WES (`wes`) |
| DDD classification | Generic |
| Tier | WES, extracted catalogue |
| Repository | [IQVO/process-path-management](https://github.com/IQVO/process-path-management) |
| Events | [process-path-management](/docs/services/process-path-management) |

This service groups the context's synchronous surface: the OLTP REST API (`openapi.yaml`) and, where the
context has one, the separate read-only reports API (`openapi-reports.yaml`) served by its `*-reports`
binary from an isolated analytical database. Endpoints are unauthenticated fleet-wide.


Operator-configurable process-path catalogue: canonical identity, the matchPrefix rule downstream consumers use to resolve a caller-supplied id to a path family, and the capabilities a station/associate must hold to work that path. This service replaces what was, before it existed, a static YAML file (warehouse-infra/config/process-paths/sortable-fc.yaml) loaded once at boot by fulfillment-execution, wes-work-planning, and workforce-management. It is the SOURCE of the process-path published language, never a consumer of anyone else's — every change here is propagated onward exclusively via Kafka (see apis/asyncapi.yaml), never through a synchronous callback into this service.
