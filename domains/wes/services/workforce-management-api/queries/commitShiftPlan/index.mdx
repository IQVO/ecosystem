## Overview
Commits a human-decided ShiftPlan: one or more PathPlan lines (path, plannedHeads, plannedRate, plannedHours), raising ShiftPlanCommitted. Validates, per line, that plannedHeads does not exceed the caller-supplied installedStations for that path (this context enforces the invariant independently — it has no dependency on Work Planning, which owns installed-station counts — the request carries the number it needs), that plannedHeads does not exceed the LIVE installed capacity fulfillment-execution reports for that path's capability (a SEPARATE, independent check — see ADR-0014; fetched fresh on every commit, and this service fails the entire commit loud, without any fallback, if fulfillment-execution cannot be reached). The capability is resolved through the process-path catalogue, never taken from pathId: a path's live ceiling is the number of stations registered with each of its declared requiredCapabilities (the smallest count when it declares several), so pathId PICK (or pick-zone-a) is checked against stations holding capability pick. A pathId the catalogue does not declare is rejected with 400 unknown-path-id. It also validates that plannedHours does not exceed plannedHeads * the configured max hours per shift. Naturally idempotent by the client-supplied (siteCode, shiftId) key (siteCode is the canonical name of the plan key, buildingId its deprecated alias with the same value and the same stored column; ADR 0035): the underlying repository upserts on that key. A blind retry would nevertheless re-publish ShiftPlanCommitted, so this route is also protected by the Idempotency-Key header (ADR-0027): a retried request with the same key and body replays the first response without committing or publishing again.




## POST `(/shift-plans)`

### Parameters
- **Idempotency-Key** (header): Caller-generated key (e.g. a UUID v4) that makes a retried request safe (ADR-0027). Clients MUST always send a non-empty value on the routes that declare it: a deployment backed by Postgres (every real deployment) rejects a request without it with 400 idempotency-key-required. It is declared optional here only because the in-memory development mode (which the contract test boots) does not enforce it. Reuse the SAME key for retries of one logical request (same body) — the first response, success or business error, is stored and replayed byte-for-byte for the key's TTL (24h by default) — and a NEW key for each new logical request. Reusing a key with a different body is rejected with 422 idempotency-key-reused.
