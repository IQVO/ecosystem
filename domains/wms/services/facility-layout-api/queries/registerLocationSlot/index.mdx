## Overview
The core operation of this service. Registering a LocationSlot is a chain-of-custody check, not a bare insert: the Site, Zone and Aisle implied by the LocationCode's segments must all resolve to existing, Active aggregates (404 if any link is missing, 409 if one exists but is no longer Active), and the slot's LocationType must satisfy every PlacementRule applicable to its Zone (422, naming the violated rule, if not). There are no orphan slots, ever.

`capacityOverride` is optional; omit it to inherit the LocationType's default envelope. The LocationCode is the slot's identity, so re-registering one already in use is a 409 — including when the existing slot is Decommissioned, since decommission is one-way and a retired code is never resurrected by re-registration. Publishes LocationSlotRegistered.





## POST `(/locations)`

### Parameters
- **Idempotency-Key** (header): Caller-generated unique key (a UUID per logical submit) that makes a retried request safe (ADR 0019). Clients MUST always send a non-empty, unique-per-submit key: the header is required whenever the service runs with Postgres — i.e. in every deployment — and an absent or empty key is answered 400 `idempotency-key-required`. A replay with the same key and the same body returns the original response verbatim; the same key with a different body is 422 `idempotency-key-reused`. It is declared `required: false` here only because the in-memory development mode (no DATABASE_URL) does not enforce the middleware and the Schemathesis contract run boots that mode.
