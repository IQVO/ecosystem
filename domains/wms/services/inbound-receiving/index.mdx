## Purpose
Everything before the first stow: advance ship notices (ASN), dock-door appointments, goods receipt and discrepancy capture. Hands received units to inventory-storage as events.

| | |
|---|---|
| Bounded context | `inbound-receiving` |
| Domain | WMS (`wms`) |
| DDD classification | Supporting |
| Tier | WMS |
| Publishes (Kafka) | `warehouse.inbound-receiving.events`<br/>`warehouse.inbound-receiving.analytics` |
| Consumes (Kafka) | `warehouse.product-master.events`<br/>`warehouse.facility.events` |
| CloudEvents type prefix | `com.warehouse.wms.inbound-receiving.` |
| Event source | `/warehouse/inbound-receiving` |
| Repository | [IQVO/inbound-receiving](https://github.com/IQVO/inbound-receiving) |

Every message is a CloudEvents 1.0 structured-mode JSON document (`application/cloudevents+json`).
`<ctx>.events` topics carry the integration contract; `<ctx>.analytics` topics carry projector input for the
context's own reports and are never consumed by another context.

## Contract


Event catalog for the **inbound-receiving** bounded context (WMS subdomain):
the inbound dock workflow of ASNs, dock appointments and receipts
(ADR 0001, ADR 0002).

**Published.** The `Asn`, `DockAppointment` and `Receipt` aggregates raise
nine events, published to `warehouse.inbound-receiving.events` through a
**transactional outbox**: the aggregate row and its already-encoded events
are written in ONE database transaction and a relay drains them to Kafka
(at-least-once; the CloudEvents `id` is stored with the outbox row, so a
retry republishes the same `id`). Consumers dedupe on `id`.
`ReceiptLineReceived` is the **handover event**: inventory-storage consumes
it and books `condition=Good` quantities into stock (ADR 0003); Damaged
quantities are recorded here and not booked.

**Consumed (ADR 0003).** `ProductRegistered` from
`warehouse.product-master.events` feeds the `known_skus` local copy
(`PRODUCT_MODE`, group from env `PRODUCT_CONSUMER_GROUP`).
`LocationSlotRegistered` and `LocationSlotDecommissioned` from
`warehouse.facility.events` feed the `dock_doors` local copy
(`DOCK_DOOR_MODE`, group from env `DOCK_DOOR_CONSUMER_GROUP`). Both modes
default to `permissive` (consumer not started); a `kafka` mode with an
unset group is a boot error.

**Analytics (ADR 0006).** The same nine events are ALSO written, in the
same transaction, to `warehouse.inbound-receiving.analytics` with the same
`type` and the same `id` per occurrence, `dataschema`
`urn:warehouse:inbound-receiving:analytics:<EventName>:v1` and payloads
equal to the integration payloads. Only this service's `inbound-projector`
consumes it; it is not an integration contract.

**Planned, not built.** warehouse-planning consuming
`DockAppointmentBooked` as inbound-labor demand is a documented future
edge. Nothing consumes that event today.

**Envelope (mandatory).** CloudEvents 1.0, structured content mode, Kafka
header `content-type: application/cloudevents+json; charset=UTF-8`.
Optional W3C trace-context headers (`traceparent`, and `tracestate` /
`baggage` when present) carry the trace of the request that wrote the
outbox row (ADR 0009); consumers may extract them, and must not require
them.
`specversion`, `id`, `source` (`/warehouse/inbound-receiving`), `type`,
`subject` (the aggregate instance id), `time`, `datacontenttype`
(`application/json`) and `dataschema`
(`urn:warehouse:inbound-receiving:events:<EventName>:v1`) are all required.
`type` = `com.warehouse.wms.inbound-receiving.<entity>.<EventName>` with
`<entity>` one of `asn`, `dockappointment`, `receipt`. Kafka key:
`asn_number` for `asn.*` and `receipt.*`, `appointment_id` for
`dockappointment.*`. `data` is snake_case, optional fields are omitted when
unset, timestamps are RFC 3339 UTC. A breaking payload change is a new
`.v2` type, never a mutation.
