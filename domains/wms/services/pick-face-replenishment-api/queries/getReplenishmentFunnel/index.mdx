## Overview
How does replenishment flow at the site? `days[]` has one row per UTC
calendar day intersecting `[from, to)` (zeros included); a day's counts
cover the part of the day inside the range. `requests_raised`,
`requests_completed` and `requests_cancelled` count the events whose
`time` fell in the window, and `units_requested` / `units_replenished`
sum their quantity. `completion_latency` is the requested-to-completed
time of the requests completed in the window whose request the
projection also saw; a request completed without a seen request counts
in `requests_completed` but has no latency. `p50_seconds` /
`p95_seconds` are linear-interpolated percentiles and are null when
`count` is 0. `policies_declared` counts the policy versions declared
in the window (the analytics-only `ReplenishmentPolicyDeclared`).
`siteId` narrows every counter to one site (omitted = every site);
`granularity` is `day` (the only bucket; the default). The data is as
fresh as `GET /reports/freshness` says.





## GET `(/reports/replenishment-funnel)`

### Parameters
- **from** (query): RFC 3339 instant, inclusive. Defaults to `to` minus 30 days.
- **to** (query): RFC 3339 instant, exclusive. Defaults to now. At most 366 days after `from`.
- **siteId** (query): Narrows every counter to one site. Omitted = every site.
- **granularity** (query): The time-bucket resolution; only `day` exists (the default).
