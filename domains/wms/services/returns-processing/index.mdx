## Contract


Event catalog for the **returns-processing** bounded context (WMS
subdomain): the reverse flow of goods — authorize a return against a
shipped order line (RMA), receive and grade it (ReturnReceipt), decide
what happens to it (Disposition) and hand restockable units back to
inventory-storage as a staged line (ADR 0001, ADR 0002).

**Published.** Three aggregates raise seven event types, published to
`warehouse.returns-processing.events` through a **transactional outbox**:
the aggregate row and its already-encoded events are written in ONE
database transaction and a relay drains them to Kafka (at-least-once; the
CloudEvents `id` is stored with the outbox row, so a retry republishes the
same `id`). `ReturnLineStaged` is the only type that asks a sibling to do
something: inventory-storage consumes it into its staged-receipt use case
(same shape as its `ReceiptLineReceived` plus `rma_id`, `disposition_id`,
`site_id`); `UnexpectedReturnReceived` is what exception-management turns
into a problem-solve case. An analytics mirror on
`warehouse.returns-processing.analytics` is planned, not built (ADR 0004).

**Consumed (ADR 0003).** `ProductClassified` from product-master, the
allocated order lines (`OrderAllocated` / `OrderPartiallyAllocated`) from
order-management and `PackageManifested` (the shipped fact per work unit,
`order_ref` = `{order_id}-line-{line_no}`) from fulfillment-execution.
Each feeds a durable local copy; no sibling is ever called live. Consumer
groups come from `PRODUCT_CLASSIFICATION_CONSUMER_GROUP`,
`ORDER_LINES_CONSUMER_GROUP` and `MANIFEST_CONSUMER_GROUP`. The consumed
messages below are the producers' own contracts, restated here and never
imported.

**Envelope (mandatory).** CloudEvents 1.0, structured content mode, Kafka
header `content-type: application/cloudevents+json; charset=UTF-8`.
Optional W3C trace-context headers (`traceparent`, and `tracestate` /
`baggage` when present) carry the trace of the request that wrote the
outbox row; consumers may extract them, and must not require them.
`specversion`, `id`, `source` (`/warehouse/returns-processing`), `type`,
`subject`, `time`, `datacontenttype` (`application/json`) and `dataschema`
(`urn:warehouse:returns-processing:events:<EventName>:v1`) are all
required. Kafka key = the subject. Type =
`com.warehouse.wms.returns-processing.<entity>.<EventName>`. A breaking
payload change is a new `.v2` type, never a mutation.
